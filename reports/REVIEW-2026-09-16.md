## 3. What was built

All four decisions answer one question: **how far does a warrant depend on the
customer's labels being right?** Before this, nothing in the customer path
answered it, while `CLAUDE.md` required inter-rater kappa beside every warrant.

**DECISIONS 197 - every certificate states its label-error tolerance.**
`1f0948c` (entry), `fa50d28` (code), `61ae98d` (review fixes).
`certify` picks the lowest threshold whose bound clears the budget, so every
certificate sits at the edge of its own budget. Two label errors flatter it: a
flagged item labelled positive that is really clean, and an unflagged item
labelled negative that is really positive. Each certificate now carries an exact
ladder for both: how many such errors take its confidence below 90%, 80% and
50%. An optional `label_2` column carries a second reviewer's labels, and the
record then reports Cohen's kappa, the disputed items, and exact bounds on
disputes in the whole file. **It changes no verdict**, and a test certifies one
file three ways -- no `label_2`, with one, and with a `label_2` contradicting
every label -- and compares the records.

**DECISIONS 198 - a recheck says how many label errors would have hidden a
revocation.** `53c2be5`, `b7ec0d2`, `4547781`.
The same two errors, counted against the revocation threshold. At 628 negatives
(the registered recheck size), a recheck at the certified rate needs 20 flagged
errors or 311 unflagged ones before the truth would have revoked; one a step
below the critical count needs 1 or 3. This corrected 197, which had stated the
figure as `critical - k`; each error adds a negative too, so the critical count
moves with `n`.

**DECISIONS 199 - the same measurement on this project's own warrants.**
`f4a0cda` (pre-registered), `c877133` (amended before the run), `bb800be`
(code), `7a6e93c` (artifact), `ae4b15b` (results). Section 4.

**DECISIONS 200 - the clean-clone gate names what it tested.** `61f895a`,
`b65220e`, `18dfbae`.
Found by Codex while the gate was running: the gate read the source's HEAD, then
cloned it as a separate step, and took provenance ~37 minutes later after the
tests. A commit during the run would have produced a record naming one commit as
tested and another in its provenance, with nothing refusing. The gate now fails
if the clone is not the commit it names, takes provenance at clone time, and
refuses to write a record whose source changed.

Customer-facing documentation: `docs/INPUT.md` (the `label_2` column),
`docs/LIMITATIONS.md` 3.6, and a README quickstart paragraph.

## 4. What was measured, including a failed prediction

**DECISIONS 199**, pre-registered before the run, amended once before the run
when wiring revealed the reference data covered one of three score sets. The
study ran this project's three measured TriviaQA probes at 20 false-positive
budgets each (60 certified rows) through the *customer* path, using the
project's own strict matching rule as a second labeller.

| Registered | Outcome |
|---|---|
| C0: the customer path reproduces the research sweep | **holds**, all 20 checkable rows |
| P1: one flagged-clean error takes every certificate below 0.95 | **holds**, highest 0.94982 |
| P2: counting every strict/lenient dispute as an error takes some certificate below 0.80 | **FAILS**. Lowest 0.8127 |

Reported as registered, over the 60 rows: **2 to 8** flagged-clean errors take a
certificate from at least 0.95 to below 0.80 confidence; confidence at the
disputes ranges 0.8127 to 0.9412; kappa between the two matching rules is
**0.8640 [0.8213, 0.9035]** over 600 pairs.

**One finding was not predicted:** the tolerance is identical across all three
detectors at every budget. At a fixed alpha with untied scores, the lowest
certifying threshold admits exactly the largest count that certifies, so the
ladders depend only on the number of negatives, the budget and alpha. A better
detector cannot buy a more label-robust certificate; by flagging more positives
it is exposed to *more* of the costly error.

Five claim rows were added to the README (87 -> 92 claims), each resolving
through `scripts/verify.py` against the artifact.

**What the study does not establish.** Strict matching is not a better labeller.
Its disagreements bound one identified ambiguity, not the label error. The error
both rules miss -- a correct answer whose wording is absent from the alias list
-- is unmeasured, and when flagged it is the costly kind: at budget 0.20, 8 of
179 flagged positives of that kind break the certificate.

## 6. Defects, which is the part worth reading

### 6.1 Four found by Codex's independent review, all reproduced here

Two are serious. Both are in the chain work (DECISIONS 193, 194) that predates
this session, and both were reproduced through the public CLI.

| Severity | Defect | Status |
|---|---|---|
| **P0** | A recheck REVOKED **by drift** can be continued: the next link on stable data returns VALID. `continue_chain` checks only the chain's own revocation, never the record's status | **fixed** on `fix/chain-integrity-8a`, suite green; awaiting Codex review (section 12) |
| **P0** | A chain record's serialized `threshold`, `mean_statistic` and `ended` can be edited without rehashing and still verify. They are hashed, but the verifier recomputes them and never compares the stored values | **fixed** on `fix/chain-integrity-8a` (section 12) |
| P1 | Grouped agreement resamples individual pairs: 400 rows that are really 4 repeated groups report the same kappa interval as 400 independent rows | Codex, on `fix/grouped-agreement`; pre-registration only so far |
| P1 | A chain record with `alpha` of 0 or NaN crashes with a traceback before any digest check | **fixed** on `fix/chain-integrity-8a` (section 12) |

**`warrant chain verify` reports zero findings on both P0 histories.** That
command is the instrument a customer would use to detect exactly this.

**1,763 tests caught none of them.** Each test checks the path its author was
thinking about: the chain tests assert the digest round-trips and that a revoked
*chain* refuses continuation, but none covers a record revoked by the *other*
failure mode, and none mutates a stored field without rehashing.

**A near-miss in the reproduction itself.** The first attempt shifted scores
upward, which raised the false-positive rate to 0.28 and made the chain's own
detector revoke; the continuation was refused for an unrelated reason and it
read as a PASS. Only a downward shift isolates the defect. A reproduction that
confirms the absence of a bug by accident is worse than none.

### 6.2 Defects in how this session worked, found by review or by rereading

- **A test run that reported success without running.** A backgrounded suite
  chained `; tail` after the runner, one named file did not exist, pytest
  collected nothing, and the task reported exit 0 -- `tail`'s status. Caught by
  reading the log. The rule against this was already written down.
- **A lint failure reached a commit** because the targeted test runs omitted the
  lint job. Found by the reviewing session's full suite.
- **A polarity error in 199's committed results**, found by rereading: the
  unmeasured alias-list error was placed in the wrong pool. Author and reviewer
  both missed it; the reviewer had checked the arithmetic and not which pool the
  sentence named. Corrected in `1463df5`.
- **A whole-file line-ending flip** in a test file, from `Path.write_text` on
  Windows: a 524-line diff for a 4-line change. Caught in review, amended before
  publication. The same mistake had happened earlier in the project.
- **A commit hash sent to the reviewing session from memory**, not read from
  `git log`, and wrong. Corrected in the next message.
- **197 stated the recheck figure as `critical - k`**, corrected in 198.

### 6.3 Open items closed by Codex's work, verified read-only here

## 12. Update, later on 2026-09-16

**The chain defects are fixed, on a branch, not yet merged.** Codex's claim on
them produced no commit for 22 hours, so this session took the repair over on
its own branch, `fix/chain-integrity-8a`, after posting the takeover. Codex
acknowledged it (board post 46), stopped its own attempt, and will review the
commits independently.

| Defect | Before, through the public CLI | After |
|---|---|---|
| Continuing after a drift revocation | accepted; the next link returned VALID; `chain verify` found nothing | refused (exit 2); `chain verify` flags such a history |
| Forged `threshold`, `mean_statistic`, `ended` | verified clean | refused as a digest finding, each field alone |
| `alpha` of 0 or NaN | traceback | refused as a `malformed` finding, no traceback |
| **A forked restart on a revoked warrant** (found from Codex's instructions, after the first pass) | exit 0, VALID record | exit 2, no record, head file unchanged |

Two things came out of the repair itself, not the review:

- **The first fix for NaN was incomplete.** The verifier hashes each whole record
  before reading its chain block, so a NaN anywhere still crashed. The
  acceptance harness caught it and it was fixed.
- **The guarantee was worded wider than the maths.** Records said alpha bounds
  "any false revocation". It bounds the chain's own statistic, and a revocation
  because the score distribution moved is a separate check with no such bound.
  The wording is corrected; the method and every existing digest are unchanged.

**Verified.** Full suite at the first pass, `20e3347`: 1,797 passed, 1 xfail, 0
failed. At the second pass, `d9fa4bf`: **1,803 passed, 1 xfail, 0 failed**, 1,804
collected. Both ran in this session's own worktree. 41 new regression tests,
including the bypasses, an ordinary chain that must keep working, and records
from before these changes that must still replay. No clean-clone gate has run on
this branch; that is the integrator's gate.

**Also fixed, in the customer documentation.** `docs/INPUT.md` said extra columns
in a customer's file are "carried into the JSON record untouched". They are not
kept at all -- shown with the project's own example, whose `captured_at` column
appears nowhere in the warrant. A customer relying on that sentence would lose
metadata they believed was retained. Corrected on `docs/evidence-handoff`.

**New documents, docs only.**

- `docs/EVIDENCE-HANDOFF.md`: what to hand a validation function. It finds that
  neither record type alone is enough. A release evaluation binds data, identity
  and expiry but carries no label-quality evidence. A certify warrant carries
  label quality but binds no data, identity or expiry, and an unchained recheck
  does not name its warrant. Seven gaps are listed as open.
- `docs/PILOT-PROTOCOL.md`: Codex's eight corrections applied. Hypotheses are kept
  as hypotheses, the alpha claim is narrowed, grouped-data rules are checked per
  command, and the RBI guidance is re-checked on its own page as still a draft.

**Still open.**

2. The grouped-kappa fix is Codex's, and has only its pre-registration.
3. Whether a plain, unchained recheck of a revoked warrant should also be refused

4. Two process slips in the repair, both corrected before anything was shared: a
